Smart assistant contract: Gemini 3.1 Flash-Lite runs only in the Firebase callable function and returns schema-constrained proposals from the shipped allowlist. The function requires the existing anonymous Firebase session, binds `GEMINI_API_KEY` from Secret Manager, accepts at most 500 input characters and six short history items, caps output at 900 tokens, and enforces 30 requests per Firebase UID per UTC day plus 500 project-wide requests per UTC month. The browser sends compact summaries only; the server rebuilds their permitted shape so full encounter notes, intake issue text, phone/email fields, and couple contact fields cannot enter the prompt, then drops any model-returned target ID that was not present in that compact context. Assistant chat text remains in memory and is not stored; only usage counters persist. When Gemini fails or reaches a cap, guided Chat stays fully viable. `GEMINI_SETUP.md` owns key creation, billing, spend-cap, secret, and deployment steps.

Install and offline contract: The page is an installable PWA with browser prompt handling, iPhone/iPad “Add to Home Screen” guidance, standalone safe-area handling, icons, manifest shortcuts for Resources, Encounters, Directory, and Reminders, and a service-worker-cached app shell that includes Chat. Offline shell availability does not promise offline Firebase publishing, encounter, directory, intake, or reminder mutations.

Remembered access contract: A successful password check stores a browser-local one-time unlock and establishes local Firebase auth persistence. Returning visits restore the workspace without another password when possible. “Lock app” clears both remembered unlock and tab state, signs out, returns to the password gate, and restores password focus. If storage is unavailable, the active session can continue but is not remembered.

Resources contract: Baked resources remain the frontend baseline. Admin additions store links and remote metadata only and reuse the public resource renderer. Supported inputs are YouTube including Shorts/mobile URLs, the exact TorahAnytime multiline format, the first Amazon product URL, and iTorah lecture URLs. Directory contract: Directory is a private contact book, not another resource-publishing or reminder queue. Name is the only required field; type is Therapist, Person, or Resource; phone, email, website, and a quick note are optional. Entries are grouped alphabetically and can be narrowed by search or All / Therapists / People / Resources filters. Available contact fields become direct Call, Text, Email, or Open actions. Edit reuses the inline entry form, Delete remains confirmed, and both preserve a predictable keyboard-focus return.

Encounter contract: Encounter entries normalize to `completed` or `scheduled`; legacy records are completed. A completed meeting needs only a name and defaults to the current date/time. A scheduled meeting uses the same fields but requires a deliberately chosen date, leaves time optional, hides follow-up, and receives a blue information treatment. Both types live in one couple timeline keyed first by intake submission and otherwise reconnected by exact normalized contact or names. New entries carry the timeline’s names, contact, Other people involved, method, intake link, root, and previous-entry identity, while Notes and event timing stay entry-specific. Each timeline row opens a native detail/edit dialog. A scheduled entry offers Edit schedule and Record outcome; the latter converts the same record to completed while letting the admin update any field and choose follow-up. Archiving/restoring still updates the whole timeline; individual deletion remains confirmed and irreversible.

Intake handoff contract: Intake forms are a view inside Encounters, not a top-level tab, and offer only “Schedule encounter.” Scheduling pre-fills names, all available phone/email details, Other people involved from `anyone_else_involved`, the presenting issue into Notes, and Phone as the starting method, but leaves the required scheduled date and optional time for the admin. Repeated scheduling from the same form appends to its existing couple timeline. Once any encounter links to an intake, its intake reminder is suppressed, while the source intake remains visible until explicitly deleted.

Reminder contract: Reminders combines durable personal items with automatic appointments and follow-ups. Personal reminders persist in `admin_manual_reminders`; reminder name is required, while date, time, and description are optional. No date or time reads “Anytime”; time without a date reads “Every day” at that local time; date-only and date-plus-time items receive Today, Tomorrow, calendar-date, and Overdue labels as appropriate. “Your reminders” appears before “Appointments & follow-ups” when both exist. Personal reminders sort by soonest timing, with untimed items after timed items and newest untimed items first; automatic items remain newest relevant first.

Personal reminder actions: Personal cards expose Edit, “Remind tomorrow,” and “Taken care of.” Edit reuses the inline editor and reveals a confirmed, irreversible Delete action. “Remind tomorrow” persists a snooze through the current local day so both the in-app list and background delivery wait until tomorrow; browser storage remains an immediate local fallback and is rolled back if the durable write fails. Confirmed “Taken care of” durably marks the personal record completed so it leaves the active list. For automatic follow-ups, the same confirmation clears the newest meeting’s follow-up flag or writes a durable intake resolution.

Automatic follow-up contract: Every unlinked, unresolved intake may create one scheduling prompt. Every active couple timeline may create at most one automatic item derived only from its newest entry. A latest scheduled entry becomes a reminder when its local calendar date arrives and suppresses older follow-up flags without appearing early; its optional time remains display context and does not delay eligibility. A latest completed entry appears only when follow-up is on. Archived timelines stay out of Reminders.

Notification contract: Notifications are optional, device-specific background push. Enabling creates a browser Push subscription owned by the current Firebase user and sends an immediate private test notification; the enabled state exposes “Turn off notifications.” Turning notifications off or locking the app deletes that device record and unsubscribes the browser. Two per-device Reminders switches control scheduled-meeting alerts and new-intake alerts, with both on by default; Chat exposes the same settings as direct buttons. A new intake sends an immediate private alert when its form is submitted, then remains eligible for the daily unresolved-intake reminder after 9:00 AM on later days. A Firebase scheduled function checks other due work every fifteen minutes using the subscription’s IANA time zone. Completed-meeting follow-ups are due daily after 9:00 AM. Scheduled encounters are due only on their scheduled calendar date, at their optional time or 9:00 AM when no time was supplied. Personal reminders honor their optional date and time and repeat daily after they become overdue until completed. Durable snoozes suppress both surface and push delivery through that local day, while per-device delivery receipts prevent duplicate sends. Push copy stays generic and never exposes couple names, contact information, or notes on the lock screen. Selecting it opens or focuses Reminders. Unsupported or blocked notification permission changes only the explanation and control state; reminders remain visible in the app.

Constraint: The owner explicitly requested that the client-side password route remain temporarily. Remembered access restores an anonymous Firebase session after the local unlock check; this is a known interim security limitation and must not be mistaken for a strong authorization boundary.
